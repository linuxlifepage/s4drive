Привет! Амбициозный и очень правильный проект. Родные клиенты для S3-хранилищ обычно ориентированы на DevOps-инженеров (вроде Cyberduck или Cyberctl), а стандартные облака (Google Drive, Dropbox) жестко привязаны к своей инфраструктуре. Создать по-настоящему быстрый, красивый и надежный GUI-клиент поверх S3 с логикой полноценного виртуального диска — это отличная ниша.

Учитывая стек (Rust + Tauri) и жесткие требования к надежности, ресурсоемкости и кроссплатформенности, давайте разберем детальную архитектуру и фазы реализации S4Drive.

---

## Архитектура ядра и технологический стек

Для обеспечения минимального потребления памяти (до 50-70 МБ в режиме фона) и мгновенного отклика (sub-100ms):

* **Core-логика (Rust):** Логика синхронизации, локальная БД метаданных, S3-клиент, криптография, сетевой стек и многопоточность реализуются строго на Rust.
* **Фронтенд (Tauri v2):** Используем Tauri 2.0, так как в нем значительно улучшена поддержка мобильных платформ (Android/iOS). Фронтенд — это исключительно легковесный UI (HTML5/CSS/TypeScript с использованием быстрого фреймворка, например, SolidJS или Svelte, чтобы не тащить тяжелый рантайм React).
* **Синхронизация (Собственный движок vs Rclone):** > **Решение:** Однозначно **собственный движок на Rust**. Встраивание Rclone как бинарника (sidecar) раздует размер сборки, усложнит управление процессами (особенно на iOS/Android, где фоновые процессы жестко ограничиваются ОС) и не позволит реализовать кастомную, транзакционную логику разрешения конфликтов на уровне метаданных. К тому же, для Rust есть отличные низкоуровневые асинхронные S3-клиенты (`aws-sdk-rust` или `opendal`).

## ФАЗА 1: Архитектура синхронизации и метаданных (Ядро надежности)

Основная проблема S3 — отсутствие встроенной POSIX-логики атомарного переименования директорий и высокая стоимость запросов листинга (`LIST`). Чтобы минимизировать конфликты и сделать синхронизацию мгновенной, вводим **Локальный индекс + Удаленный журнал**.

### 1.1. Движок метаданных (Локально)

На каждом устройстве разворачивается легковесная, транзакционная встроенная БД на Rust (например, **Redb** или **Fjall** для максимальной скорости и корректного завершения при сбоях питания, либо классический SQLite через `rusqlite`).

* **Структура индекса:** Хранит дерево файлов, локальные пути, удаленные S3-ключи, размеры, `blake3` или `sha256` хеши, таймстампы модификации (`mtime`) и текущий статус (`Synced`, `Pending`, `Conflict`).
* **Виртуальные папки:** S3 не знает, что такое "папка" (это просто префиксы). Локальная БД абстрагирует это в полноценное дерево для UI.

### 1.2. Стратегия синхронизации и предотвращения конфликтов

Поскольку к одному бакету могут одновременно обращаться несколько инстансов S4Drive (или LLM-агенты), чистый "state-based" подход (сравнение таймстампов) приведет к потере данных (race conditions).

* **Двунаправленный Sync через Vector Clocks (Векторные часы):** Каждый файл/объект снабжается мета-атрибутами S3 (Metadata), содержащими идентификатор устройства (`device_id`) и логический счетчик версий.
* **Атомарный коммит:** Перед загрузкой измененного файла S4Drive проверяет `ETag` (хеш) и версию объекта в S3. Если удаленная версия изменилась с момента последнего сканирования, файл не перезаписывается "в лоб".
* **Стратегия разрешения конфликтов (Conflict Resolution):**
1. **Авто-разрешение (Deterministic):** Если изменения не пересекаются (например, разные файлы в одной папке), индекс обновляется автоматически.
2. **Вилка версий (Forking):** Если файл изменен одновременно на двух устройствах, движок создает рядом файл конфликта: `Document (Conflict from MacBook-Pro 2026-05-30).docx`. При этом оригинальный файл в базе помечается флагом конфликта для UI.
3. **Локальный лог изменений (WAL):** Все локальные операции файловой системы перехватываются через `notify` (в Linux/Windows/MacOS) и пишутся в Write-Ahead Log.

## ФАЗА 2: Кроссплатформенный жизненный цикл и Системный Трей

Приложение должно вести себя нативно на всех ОС. Основная бизнес-логика работает в Rust-state, UI — лишь проекция.

### 2.1. Десктоп-специфика (Windows, Linux, macOS)

* **Tray-First инициализация:** При старте ОС приложение запускается "вслепую". Окно UI не инициализируется в памяти, пока пользователь не кликнет по иконке в трее (экономия RAM).
* **Поведение окна:** Окно имеет фиксированный или средний размер (`width: 400px-500px`, `height: 600px` в стиле виджета Dropbox). Флаг `resizable: false` (или ограничение минимума).
* **Перехват закрытия:** Событие `tauri::WindowEvent::CloseRequested` перехватывается в Rust. Вместо разрушения окна вызывается метод `app_handle.hide()`.
* **Контекстное меню трея:** Реализуется через нативные API ОС (средствами Tauri). Элементы: *Открыть S4Drive*, *Статус синхронизации (Пауза/Продолжить)*, *Настройки*, *Выход*. Полное закрытие (`std::process::exit(0)`) происходит *только* через явный клик на "Выход" в трее.

### 2.2. Мобильная специфика (Android, iOS)

* Мобильные ОС убивают фоновые процессы. Никакой постоянной синхронизации "в фоне" как на ПК там быть не может.
* **Решение:** Использование Push-уведомлений (Silent Pushes via Firebase/APNS) или системных Background Tasks (WorkManager в Android, BackgroundTasks в iOS) для периодического пробуждения ядра Rust (например, раз в 15 минут или при смене геопозиции/подключении к Wi-Fi) для быстрой сверки метаданных.
* Интерфейс на мобильных устройствах открывается на весь экран, трей отсутствует, навигация переключается на стандартный мобильный UX (Bottom Navigation).

## ФАЗА 3: Проектирование UI/UX интерфейса (Прогрессивный минимализм)

Интерфейс должен скрывать сложность S3 (бакеты, регионы, endpoint'ы) от обычного пользователя.

### 3.1. Логическая структура экранов (Десктоп виджет)

* **Header:** Название текущего бакета/аккаунта, индикатор глобального статуса ("Синхронизировано", "Загрузка 3 файлов, 45 МБ/с", "Пауза"). Иконка шестеренки (настройки).
* **Основная зона (Переключаемая):**
* *Вкладка "Файлы":* Проводник по виртуальной структуре папок бакета. Поддержка Drag-and-Drop для быстрой загрузки файлов прямо в окно трея.
* *Вкладка "Активность":* Список последних измененных файлов и лог конфликтов, если они возникли.


* **Footer:** Информация о дисковом пространстве (объем данных в бакете) и быстрая кнопка "Открыть локальную папку синхронизации".

### 3.2. Нативное контекстное меню файлов

* **Внутри UI:** Клик правой кнопкой мыши по элементу внутри Tauri-окна вызывает кастомное, плавное HTML-меню. Команды: *Поделиться (генерация Pre-signed URL)*, *Посмотреть версии*, *Сделать доступным только в облаке / Скачать локально*, *Удалить*.
* **Интеграция в ОС (Перспектива):** Интеграция в Проводник Windows (реестр) и macOS Finder (Finder Extensions) для отображения статусных иконок (зеленая галочка, синие стрелочки синхронизации) прямо на файлах в системе.

## ФАЗА 4: Безопасность, Версионирование и Оптимизация сети

### 4.1. Сетевая оптимизация и работа с S3

* **Multipart Uploads:** Файлы крупнее 5 МБ автоматически бьются ядром Rust на чанки и загружаются параллельно в несколько потоков. При обрыве связи загрузка возобновляется с недозагруженного чанка.
* **Пул соединений:** Использование `hyper` / `reqwest` с поддержкой HTTP/2 и HTTP/3 (QUIC) для минимизации задержек (RTT) при общении с S3 API.
* **Трафик-шейпинг:** Возможность в настройках ограничить скорость отдачи/загрузки, чтобы не забивать канал пользователя.

### 4.2. Версионирование и жизненный цикл

* Приложение проверяет, включен ли в S3-бакете таргетинг версий (Versioning).
* Если включен, при клике на файл в контекстном меню "История версий" S4Drive делает запрос `ListObjectVersions` и выводит список прошлых модификаций с возможностью "Откатиться" (сделать старую версию актуальной).

## ПОШАГОВЫЙ ПЛАН РЕАЛИЗАЦИИ

```
[ФАЗА 1: CORE (Rust)] ──► [ФАЗА 2: СИНХРОНИЗАЦИЯ] ──► [ФАЗА 3: TRAY & UI (Tauri)] ──► [ФАЗА 4: МОБИЛЬНЫЕ & ОПТИМИЗАЦИЯ]

```

### Этап 1: Проектирование Ядра (Rust)

1. Разработка архитектуры локальной БД метаданных (схема таблиц индексов, папок, воркеров).
2. Реализация низкоуровневого S3-клиента на Rust с поддержкой дедупликации чанков и параллельной сборки.
3. Покрытие юнит-тестами логики вычисления векторных часов и сценариев разрешения конфликтов (когда 3 абстрактных устройства одновременно меняют один индекс).

### Этап 2: Интеграция с ОС и Трей (Tauri + Rust)

1. Настройка конфигурации Tauri под кроссплатформенную сборку (блокировка закрытия окна, скрытие из панели задач).
2. Написание платформозависимого кода для системного трея (Windows/macOS/Linux).
3. Создание IPC-каналов (Tauri `commands`) для передачи состояния синхронизации из бэкенда Rust во фронтенд в реальном времени.

### Этап 3: UI/UX и Контекстные действия

1. Верстка интерфейса (дизайн а-ля компактный виджет). Оптимизация рендеринга больших списков файлов (Virtual Scrolling).
2. Реализация логики Drag-and-Drop и контекстных меню.
3. Добавление экрана конфигурации: ввод S3 Credentials (Access Key, Secret Key, Endpoint, Bucket Name) с валидацией "на лету".

### Этап 4: Адаптация под Мобильные платформы и Стабилизация

1. Оптимизация UI под мобильные экраны (тач-события, жесты свайпа для удаления/шаринга).
2. Настройка Background Tasks для iOS и Android в Tauri v2 для периодической фоновой проверки обновлений в бакете.
3. Стресс-тестирование: внезапное отключение сети посреди загрузки файла, изменение файлов LLM-скриптами на высокой скорости, проверка утечек памяти (цель — стабильные <60MB RAM на десктопе в фоне).
