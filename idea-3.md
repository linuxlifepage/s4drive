Ниже представлен детальный план реализации S4Drive — кросс-платформенного GUI-клиента с S3-бакетом в роли основного хранилища. План разбит на шесть фаз: от архитектурного проектирования до распространения. Акцент сделан на логику работы, выбор компонентов, надёжность синхронизации и оптимизацию ресурсов. ## Фаза 1. Исследование и архитектурное проектирование (4–6 недель)

### 1.1 Уточнение функциональных требований
- Работа приложения строго через S3-совместимое хранилище (один бакет = один «диск»).
- Полная двусторонняя синхронизация между всеми устройствами пользователя.
- Фоновый режим с иконкой в системном трее (desktop) / постоянным уведомлением (mobile).
- Главное окно среднего размера с файловым менеджером, настройками, статусом синхронизации.
- Закрытие окна сворачивает приложение в трей, полный выход — через контекстное меню трея.
- Контекстное меню файла (открыть, скачать, поделиться ссылкой, версии, свойства).
- Бесконфликтная или минимально конфликтная синхронизация даже при одновременном редактировании на разных устройствах.

### 1.2 Выбор технологического стека
- **Ядро (синхронизация, S3, БД, вотчеры): Rust**  
  Причины: производительность, безопасность памяти, единая кодовая база для всех платформ, идеальная интеграция с Tauri.
- **GUI-фреймворк: Tauri 2.x**  
  Даёт нативный WebView + Rust-бэкенд на десктопах (Windows, Linux, macOS) и поддержку Android/iOS через единый проект.
- **Фронтенд UI: Solid.js / Svelte** (легковесные, реактивные) + TypeScript.  
  Компилируется в статику, работает внутри Tauri WebView.
- **Локальная БД: SQLite** (через `rusqlite` в Rust).  
  Хранит индекс синхронизации, журнал операций, учётные данные.
- **S3-клиент: `aws-sdk-s3` для Rust** (официальный AWS SDK).  
  Поддерживает multipart-загрузку, управление ETag, кастомные метаданные, совместим с любыми S3-провайдерами.
- **Вотчер ФС: `notify` crate** (кроссплатформенный, 5 ОС).
- **Трей: `tray-icon` crate** (или встроенный API Tauri для systray).
- **Хранение секретов: системный keychain** через `keyring` crate.

**Почему не rclone / s3cmd?**  
Эти утилиты — CLI-инструменты, не дающие синхронного API для GUI, не позволяющие тонко управлять конфликтами в реальном времени, не интегрируются с мобильными платформами. Собственный движок на Rust даёт полный контроль, лучшую производительность и единое поведение на всех ОС.

### 1.3 Архитектурное проектирование
Приложение разделяется на три изолированных слоя:

- **Core Service (Rust)** – фоновый демон, работающий в отдельном потоке. Отвечает за синхронизацию, S3-взаимодействие, отслеживание ФС, разрешение конфликтов.
- **API Layer (Tauri Commands)** – мост между Core Service и UI. Предоставляет команды: список файлов, статус, настройки, действия над файлами.
- **UI (Web frontend)** – отображает данные, вызывает команды, не содержит бизнес-логики синхронизации.

Core Service внутри устроен как асинхронный рантайм с циклом событий:  
`Локальные изменения → Очередь → Загрузка на S3` и `Таймер → Поллинг S3 → Загрузка локальных изменений с других устройств`.  
Работает постоянно в фоне, даже когда UI скрыт.

### 1.4 Модель данных синхронизации и стратегия разрешения конфликтов
**Локальная база SQLite (по одной на устройство):**
- `accounts` – данные подключения (endpoint, bucket, шифрованные ключи).
- `sync_folders` – локальная папка ↔ бакет (префикс).
- `objects` – каждая запись соответствует файлу/папке:
  - `local_path` (относительно корня синхронизации),
  - `s3_key`,
  - `local_mtime`, `local_hash` (SHA-256),
  - `remote_etag`, `remote_mtime` (LastModified из S3),
  - `state` (Synced, ModifiedLocally, ModifiedRemotely, Conflicted),
  - `version_vector` (логические часы) – для обнаружения параллельных изменений.
- `operation_log` – журнал всех операций (создание, изменение, удаление) с временными метками и идентификатором устройства.

**Стратегия синхронизации без сервера координации (peer-to-S3):**
- Каждое устройство имеет уникальный ID (UUID).
- При локальном изменении файла вычисляется хэш нового содержимого, записывается в журнал с указанием ID устройства и монотонно возрастающим счётчиком версий.
- Загрузка на S3 всегда условная: перед PUT проверяется, что текущий ETag объекта совпадает с тем, который устройство видело последним (conditional write через заголовок `If-Match`).  
  - Если совпал — загрузка успешна, обновляется локальная запись.
  - Если не совпал (HTTP 412 Precondition Failed) — значит другой клиент уже изменил объект. Запускается процедура разрешения конфликта.
- Разрешение конфликта **для файлов**:
  1. Скачать текущую версию из S3 (новую).
  2. Создать конфликтную копию на S3 с именем `filename (Conflict from <Device ID> <Date>).ext`.
  3. Локально сохранить обе версии: текущая версия из S3 замещает локальный файл (или пользователь выбирает), конфликтная копия помещается рядом.
  4. Уведомить UI о конфликте с возможностью ручного разрешения.
- Конфликты **директорий** (структурные) обрабатываются атомарными операциями с использованием префиксов и контрольных списков. Удаление папки реализуется как удаление всех объектов с префиксом, с осторожной проверкой.

**Почему не CRDT / бесконфликтные структуры?**  
Полноценные CRDT для файловой системы (как в Dropbox с синхронизацией папок) крайне сложны и могут приводить к неожиданным результатам с бинарными файлами. Выбран гибридный подход: условная запись + автоматическое создание конфликтных копий при параллельном редактировании. Он предсказуем и не теряет данные. Для обычных пользователей, работающих над одним файлом по очереди, конфликт не возникает. Для ИИ-агентов и совместной работы конфликтные копии — приемлемый компромисс.

### 1.5 UI/UX концепция и логика поведения
- **Главное окно:** средний размер (например, 900×650 px), адаптивная вёрстка.  
  - Левая панель: дерево папок / быстрый доступ.  
  - Центр: список файлов с иконками, размером, датой изменения, индикатором синхронизации (зелёная галочка, синяя стрелка, красный восклицательный знак).  
  - Правая панель: детали выбранного файла, история версий (опционально).  
- **Контекстное меню файла:** открыть, скачать на устройство (если облачный), поделиться временной pre-signed ссылкой, просмотр истории версий, свойства.
- **Поведение трея:**  
  - Клик левой кнопкой — показать/скрыть окно (если скрыто, окно появляется в центре экрана).  
  - Правый клик — меню: Открыть S4Drive, Статус синхронизации, Пауза/Возобновить, Настройки, Выйти.
- **Мобильная версия:** аналогичный интерфейс, адаптированный под тач, без трея — вместо него постоянное уведомление о работе сервиса. Фоновый сервис запускается при старте ОС.

## Фаза 2. Разработка ядра синхронизации на Rust (8–10 недель)

### 2.1 Инициализация проекта и базовая структура
- Создание Tauri-проекта с плагинами: `tauri-plugin-sql` (SQLite), `tauri-plugin-fs`, `tauri-plugin-notification`.
- Реализация модуля конфигурации: чтение/запись настроек, миграции БД.

### 2.2 Модуль S3-клиента
- Асинхронная обёртка над `aws-sdk-s3`.
- Функции: `list_objects(prefix)`, `head_object(key)` → метаданные, `put_object(key, body, expected_etag)`, `get_object(key)`, `delete_object(key)`, `copy_object` (для конфликтных копий).
- Поддержка multipart-загрузки с возобновлением для больших файлов.
- Логика сравнения удалённого состояния на основе `LastModified` и `ETag`.

### 2.3 Модуль локального индекса (SQLite)
- Реализация DAO для таблиц `sync_folders`, `objects`, `operation_log`.
- Методы: добавить/обновить файл, пометить состояние, получить список объектов по префиксу, найти конфликты.
- Эффективная работа с путями: хранение относительных путей с нормализацией.

### 2.4 Модуль вотчера файловой системы
- Интеграция с `notify`: подписка на рекурсивные события в выбранной папке.
- Дедупликация событий (ОС иногда шлёт множественные ивенты).
- Фильтрация временных файлов, системных скрытых элементов.
- Генерация внутренних событий: `FileCreated`, `FileModified`, `FileDeleted`, `FileRenamed`.
- События ставятся в очередь с приоритетами (удаление важнее создания).

### 2.5 Движок синхронизации (Core Service)
- Цикл обработки событий, работающий в собственном потоке Tokio.
- **Обработка локальных изменений:**
  1. Из очереди извлекается событие.
  2. Для новых/изменённых файлов вычисляется SHA-256, сравнивается с последней известной локальной версией. Если хэш совпадает — игнорируется.
  3. Проверяется, не запрещена ли синхронизация (файл заблокирован).
  4. Выполняется условная загрузка на S3:  
     - Если объект существует и его `ETag` в локальной БД == текущий удалённый `ETag` → PUT с `If-Match`.  
     - Если объект новый → безусловный PUT.  
     - Если `ETag` не совпал → запуск обработчика конфликта (скачать новую версию, создать конфликтную копию, уведомить UI).
  5. После успешной загрузки обновляется запись в `objects` (ETag, mtime, state=Synced).
- **Обработка удалённых изменений (поллинг S3):**
  - Каждые N секунд (настраивается, по умолчанию 30 с) выполняется `list_objects` с маркером последнего известного состояния (хранится маркер ContinuationToken и временная метка последней проверки).
  - Для каждого объекта сравнивается `ETag/LastModified` с локальной записью. Если изменилось:
    - Если локальный файл не изменялся → скачать новую версию и заменить локально, обновить БД.
    - Если локальный файл также изменён (state=ModifiedLocally) → применить стратегию условной загрузки при следующем локальном цикле (или сразу инициировать разрешение).
  - Обнаружение удалённых объектов: если в S3 объект отсутствует, а локально он есть и помечен как синхронизированный → удалить локально (или переместить в корзину). Если локально изменён — сохранить и предложить повторно загрузить.

### 2.6 Фоновый режим и управление жизненным циклом
- Запуск Core Service при старте приложения (до показа UI).
- При сворачивании окна UI скрывается, Core Service продолжает работу.
- Реализация Tauri-команд: `pause_sync`, `resume_sync`, `get_status`, `shutdown`.
- Интеграция с системным треем через `tray-icon` или Tauri API: создание иконки, меню, обработка кликов.

### 2.7 Безопасность
- Ключи S3 хранятся в системном Keychain (Windows Credential Manager, macOS Keychain, Linux Secret Service).
- При запуске запрашивается разблокировка ключей (если ОС требует).
- Сетевое взаимодействие только по HTTPS с валидацией сертификатов.

### Итоговое резюме архитектурных решений
- **Ядро синхронизации** целиком на Rust, встроено в Tauri-приложение как sidecar-сервис, что обеспечивает максимальную производительность и контроль.
- **Локальная SQLite** хранит полную картину состояния, позволяя быстро стартовать и корректно обрабатывать конфликты.
- **Условные PUT-запросы (ETag)** гарантируют целостность данных в распределённой среде без центрального сервера.
- **Автоматическое создание конфликтных копий** предотвращает потерю данных и даёт пользователю возможность ручного выбора.
- **UI отделён от логики** и может развиваться независимо, используя современный лёгкий веб-стек.
- Приложение полностью соответствует требованиям: оптимизировано по ресурсам, надёжно, кроссплатформенно, работает в фоне, интерфейс логичен и прост.
